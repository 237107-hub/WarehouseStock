# Стандарт кодування WarehouseStock

## 1. Загальні положення

Стандарт застосовується до коду бібліотеки WarehouseStock.Core
і консольного застосунку WarehouseStock.App.

1. Мова проєкту — C#, цільова платформа — net8.0.
2. Аналіз nullable-посилань увімкнений в обох проєктах.
3. Грошові значення зберігаються в decimal, кількість одиниць — в int.
4. Час створення документа зберігається в DateTimeOffset.
5. Числа в демонстраційному виводі форматуються з InvariantCulture.
6. Після завершення етапу збірка не повинна мати помилок і попереджень.

Документ переміщення містить ідентифікатори складів відправлення
та призначення. Позиція містить артикул, кількість і облікову ціну.
Підсумок документа дорівнює сумі вартостей усіх його позицій.

## 2. Іменування

| Сутність | Конвенція | Приклад | Антиприклад |
|---|---|---|---|
| Клас | PascalCase, іменник | TransferLine | transferline |
| Інтерфейс | I + PascalCase | ITransferRepository | Repository |
| Метод | PascalCase, дієслово | AddLine | add_line |
| Властивість | PascalCase | UnitPrice | unit_price |
| Приватне поле | _camelCase | _lines | m_Lines |
| Параметр | camelCase | sourceWarehouseId | SourceWarehouseId |
| Локальна змінна | camelCase | totalAmount | ta |
| Константа | PascalCase | MaxLineCount | MAX_LINES |
| Перелічення | PascalCase, однина | TransferStatus | TransferStatuses |
| Значення перелічення | PascalCase | InTransit | in_transit |

Назви мають передавати зміст предметної області.
Скорочення на кшталт tr, qty та wh у новому коді не використовуються.
Sku та Id дозволені як усталені позначення.
Ім'я файлу публічного типу збігається з ім'ям цього типу.

## 3. Форматування

1. Один рівень відступу — 4 пробіли; табуляція заборонена.
2. Довжина рядка — до 100 символів.
3. Фігурна дужка блоку відкривається на новому рядку: стиль Allman.
4. Блоки if, foreach та інших керувальних конструкцій мають дужки,
   навіть коли містять одну інструкцію.
5. Між членами класу залишається один порожній рядок.
6. Наприкінці файлу має бути переведення рядка.
7. Пробіли в кінці рядків видаляються.
8. Файли коду зберігаються в UTF-8, переведення рядків — CRLF.
9. Директиви using розташовуються перед файловим простором імен.
10. Директиви System розташовуються першими; невикористані видаляються.
11. Для просторів імен використовується форма namespace X;.
12. Поля розташовуються перед властивостями, методи — після властивостей.
13. Типи локальних змінних зазначаються явно.

Для автоматичного виправлення використовується dotnet format.
Параметр max_line_length є домовленістю редактора;
дотримання межі 100 символів додатково перевіряється під час огляду.

## 4. Коментарі та документація

Коментар пояснює причину рішення, припущення або обмеження.
Коментарі, що лише повторюють інструкцію, не додаються.

Поганий приклад:

    // Збільшуємо кількість на одиницю.
    quantity = quantity + 1;

Корисний приклад для майбутнього розрахунку упаковок:

    // Неповна коробка також займає окреме місце на складі.
    decimal boxCount = Math.Ceiling(quantity / unitsPerBox);

Публічні типи описуються XML-коментарем summary.
Для документованих методів параметри пояснюються тегом param,
а повернене значення — тегом returns.
Коментарі пишуться українською мовою, ідентифікатори — англійською.

Повноту документації всіх публічних членів буде запроваджено з ЛР №4.
До цього етапу відповідні правила вимкнено з поясненням у .editorconfig.
Наявні XML-коментарі мають бути змістовними й узгодженими з кодом.

## 5. Структура проєкту

1. WarehouseStock.Core містить типи предметної області й розрахунки.
2. WarehouseStock.App відповідає за створення прикладу та консольний вивід.
3. App посилається на Core; зворотне посилання заборонене.
4. У Core не додаються виклики Console.ReadLine та Console.WriteLine.
5. У теці Domain кожен публічний тип розміщується в окремому файлі.
6. Згенеровані теки bin та obj не додаються до Git.
7. Локальні файли data/*.local.json та *.user не додаються до Git.
8. Зміни доменної логіки не повинні залежати від оформлення консолі.

На етапі ЛР №1 типи утворюють мінімальний скелет.
Додаткові перевірки, інкапсуляція та керування станами
впроваджуватимуться послідовно в наступних роботах.

## 6. Правила комітів

Один коміт відповідає одній завершеній зміні.
Перед комітом перевіряються git status --short і результат збірки.
До коміту не включаються сторонні файли та результати складання.

Формат повідомлення: тип: короткий опис зміни.
Використовуються типи feat, fix, docs, chore та style.
Приклад: feat: додано доменний скелет складського обліку.
Повідомлення на кшталт «зміни», «готово» та «asdf» не допускаються.

Робоча гілка — main. Завершення першої роботи позначається тегом lab1.
Історія зберігається разом із проєктом і входить до результату роботи.

## 7. Правила, закріплені машинно

| Правило стандарту | Механізм | Налаштування або код |
|---|---|---|
| Відступ 4 пробіли | .editorconfig | indent_size = 4 |
| Пробіли замість табуляції | .editorconfig | indent_style = space |
| UTF-8 | .editorconfig | charset = utf-8 |
| Кінцеве переведення рядка | .editorconfig | insert_final_newline = true |
| Приватні поля _camelCase | Аналізатор іменування | private_fields_rule, IDE1006 |
| Параметри camelCase | Аналізатор іменування | locals_rule, IDE1006 |
| Типи та методи PascalCase | Аналізатор іменування | members_rule, IDE1006 |
| Інтерфейси I + PascalCase | Аналізатор іменування | interfaces_rule, IDE1006 |
| Обов'язкові дужки | Правила стилю | csharp_prefer_braces, IDE0011 |
| Файлові простори імен | Правила стилю | IDE0161 |
| Немає зайвих пробілів | StyleCop | SA1028 |
| Порядок членів класу | StyleCop | SA1201 |
| Дужки керувальних блоків | StyleCop | SA1503 |
| Порожні рядки між членами | StyleCop | SA1516 |
| Оформлення коду | dotnet format | IDE0055 |
| Nullable-аналіз | Компілятор | Nullable = enable |
| Перевірки під час збірки | MSBuild | EnforceCodeStyleInBuild = true |

SA1633 вимкнено: навчальні файли не потребують ліцензійних заголовків.
SA1101 вимкнено: стандарт допускає звертання до членів без this.
SA1309 вимкнено: проєкт використовує приватні поля з префіксом _.
SA0001 та SA1600–SA1602 вимкнено до етапу повної XML-документації.

Решта перевірок StyleCop залишається активною.
Нові вимкнення правил потребують окремого пояснення в .editorconfig.
Вимкнення всіх правил одним загальним налаштуванням не допускається.
